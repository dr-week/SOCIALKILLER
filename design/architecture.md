# AI Marketing Orchestrator – Design Overview

## 1️⃣ System Overview
The platform is split into three logical layers:

| Layer | Responsibility | Primary Tech |
|------|----------------|-------------|
| **Browser Extension** | Interacts with the UI of social platforms. Provides a side‑panel UI for the AI operator, injects content scripts to read/act on pages, and forwards events to the backend. | Manifest V3, Service Worker, Content Scripts, HTML/JS UI |
| **Backend Engine** | Stores brand profiles, job definitions, schedules, policies, and results. Executes deterministic actions (e.g., API calls, media validation) and orchestrates AI‑driven steps. | Node 24, Express/Fastify, SQLite (existing), TypeScript |
| **Publishing / Engagement Adapters** | Platform‑specific modules that translate **universal actions** into concrete API calls or DOM interactions. | TypeScript modules – `facebookAdapter.ts`, `twitterAdapter.ts`, `instagramAdapter.ts`, … |

The extension is **the only component that manipulates the DOM**; the backend is the source‑of‑truth for job state.

## 2️⃣ Universal Action Contract
All automation is expressed as a **plain JSON action** that conforms to a strict schema.  The contract lives in `backend/src/action_contract.ts`.

```ts
/**
 * The platform that the action targets (e.g. "twitter", "instagram", "linkedin").
 */
export type PlatformId = 'twitter' | 'instagram' | 'linkedin' | 'facebook' | 'tiktok' | string;

/**
 * Base interface common to every action.
 */
export interface BaseAction {
  /** Unique identifier for the action instance. */
  id: string;
  /** Human‑readable description (used for UI approval). */
  title: string;
  /** Target platform. */
  platform: PlatformId;
  /** Account identifier (e.g. username or numeric id). */
  accountId: string;
  /** Whether this action mutates external state. */
  mutates: boolean;
  /** Permissions required – used by the permission manager. */
  requiredPermissions: string[];
  /** Optional approval flag – `true` means the UI must approve before execution. */
  requiresApproval?: boolean;
  /** Maximum time the backend may spend on the action (ms). */
  timeoutMs?: number;
  /** Retry policy – number of attempts before giving up. */
  retry?: number;
}

/** Specific actions – extend `BaseAction` with a payload that matches the operation. */
export interface InspectPageAction extends BaseAction {
  type: 'inspect_page';
  /** CSS selector or XPath expression to capture. */
  selector: string;
}

export interface CreatePostAction extends BaseAction {
  type: 'create_post';
  /** Text content of the post (may include placeholders). */
  caption: string;
  /** URLs of images / videos to attach. */
  mediaUrls?: string[];
  /** Optional carousel definition for platforms that support it. */
  carousel?: { mediaUrls: string[]; captions?: string[] };
}

export interface ReplyToCommentAction extends BaseAction {
  type: 'reply_to_comment';
  /** Identifier of the comment to reply to (platform‑specific). */
  commentId: string;
  /** Reply text. */
  reply: string;
}

export interface SendCustomerReplyAction extends BaseAction {
  type: 'send_customer_reply';
  /** Conversation/channel identifier. */
  threadId: string;
  /** Drafted reply (generated by the AI). */
  reply: string;
}

export type Action =
  | InspectPageAction
  | CreatePostAction
  | ReplyToCommentAction
  | SendCustomerReplyAction
  // …add more as needed
  ;

/** Result returned to the client after execution. */
export interface ActionResult {
  id: string;
  success: boolean;
  /** Arbitrary payload – e.g. post URL, comment ID, error message. */
  data?: any;
  /** Human‑readable error if `success` is false. */
  error?: string;
}
```

## 3️⃣ Safety & Policy Layer
* **Approval Workflow** – Any action with `requiresApproval:true` is pushed to the side‑panel UI. The user must explicitly click **Approve** before the backend executes it.
* **Duplicate Prevention** – Before persisting a `generated_drafts` entry the engine checks the unique `(brandId, platformId, topicKey)` and `(brandId, platformId, contentHash)` constraints (already present in the SQLite schema).
* **Rate‑limit & Quota** – Each platform adapter respects the platform’s published limits; the backend throttles jobs per account.
* **Audit Log** – Every action, who approved it, and the result is stored in `activity_logs`.
* **CAPTCHA / Auth Guard** – The extension never automates login flows; the user must be logged‑in. If a CAPTCHA appears the action is paused and reported.

## 4️⃣ Extension Architecture (Manifest V3)
```
extension/
│   manifest.json          ← declares permissions, side‑panel, service‑worker
│   service_worker.js      ← background, routes messages, schedules jobs
│   content_script.js      ← runs in page context, reads DOM, performs safe clicks
│   side_panel.html        ← UI for the AI operator
│   side_panel.js          ← UI logic, shows pending approvals, job history
└─ icons/ …                ← 16/48/128 px icons
```
* **Service Worker** keeps a long‑lived WebSocket / HTTP connection to the backend for real‑time status updates.
* **Content Script** is injected only on URLs that a platform adapter declares as needed (e.g. `*://*.twitter.com/*`).
* **Permission Manager** (in the service worker) requests host permissions on‑demand via `chrome.permissions.request`.

## 5️⃣ Backend Engine Sketch
```
backend/
│   src/
│   │   server.ts                 ← Express / Fastify entry point
│   │   job_queue.ts              ← In‑memory + SQLite persistence of jobs
│   │   action_contract.ts         ← Types (see above)
│   │   action_registry.ts         ← Map<action.type, handler>
│   │   adapters/
│   │       twitterAdapter.ts
│   │       instagramAdapter.ts
│   │       …
│   └─ utils/
│           validation.ts
│           logger.ts
└─ package.json
```
* **Job Queue** – stores a `jobs` table (`id`, `brandId`, `actionJson`, `status`, `scheduleAt`, …). Workers poll the queue, validate the action against the contract, ask the UI for approval if needed, then call the appropriate platform adapter.
* **Policy Engine** – evaluates `requiresApproval`, duplicate checks, and user‑defined limits before enqueuing.
